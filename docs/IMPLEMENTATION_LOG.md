## Entries

- 2026-08-24: Resolved the Phase 01A design-system path discrepancy by moving the authoritative file from `docs/DESIGN_SYSTEM.md` to `docs/08-design/DESIGN_SYSTEM.md` without changing its contents. There is one authoritative copy.
- 2026-08-24: Phase 01B generated the initial Drizzle migration and added isolated PostgreSQL integration tests. Live migration and integration verification could not run because Docker Desktop's daemon is unavailable; no database URL, credential, or environment file was created as a workaround.
- 2026-08-24: Phase 01B readiness now keeps the API process alive during temporary PostgreSQL outages while `/ready` returns `503 DEPENDENCY_UNAVAILABLE`; invalid or missing database configuration still fails startup. The initial migration no longer installs `pgcrypto`: PostgreSQL 17 provides the `gen_random_uuid()` UUID strategy used by the schema as a core function.
- 2026-08-24: Updated development tooling to ESLint 10 and Drizzle Kit `1.0.0-rc.4`. The registry reports that the 1.0 beta line is superseded by this maintained release candidate. It removes the deprecated `@esbuild-kit/*` loader packages. Drizzle Kit RC imports an internal Drizzle ORM API unavailable in the previous 0.44 line, so `drizzle-orm` was upgraded to the matching `1.0.0-rc.4` release candidate. Its official `drizzle-kit up` conversion moved the existing migration to the supported folder format without changing its SQL; database-client initialization was adapted to the matching RC API.
- 2026-08-24: The database migration runner now returns a sanitized diagnostic code for missing `DATABASE_URL` or an otherwise failed migration. It retains a non-zero exit and never prints connection strings, credentials, or raw database errors.
- 2026-08-25: Phase 01B PostgreSQL and Database Foundation was verified against a real local PostgreSQL 17 container and separate `slotlyflow_test` database. `pnpm db:migrate` and `pnpm db:test` passed; the integration suite verified clean migration, required tables, timezone-aware timestamps, indexes, uniqueness and foreign-key constraints, membership constraints, session/token lifecycle fields, and audit references. Overall Phase 01 remains `IN_PROGRESS`; Phase 01C has not started.
- 2026-08-25: Centralized the web-only official Next Core Web Vitals and React Hooks flat lint configuration. The maintained aggregate Next config currently loads a React plugin incompatible with ESLint 10, so the compatible official plugins are registered directly. Turbo test tasks now correctly declare no persistent outputs.
- 2026-08-25: Phase 01C-B is blocked for the registration/session behavior pending an explicit product-security decision. The Phase 01 documents require registration and email verification but do not specify whether an unverified email/password registration may receive an authenticated session. This materially changes the public authentication contract and security posture, so the API implementation will not guess.
- 2026-08-25: Phase 01C-B decision: local email/password registration creates an unverified user and verification-token flow but no application session. Verification transactionally marks the email verified, consumes the token, and issues the normal secure session. Unverified local login returns the safe typed `EMAIL_VERIFICATION_REQUIRED` state. A future validated Google identity with a provider-verified email may create a session immediately.
- 2026-08-25: Phase 01C-B uses double-submit CSRF protection for state-changing authentication endpoints: a non-HttpOnly CSRF cookie must match the `x-csrf-token` request header, while the session cookie remains HttpOnly. Authentication rate limiting is behind a process-local adapter with explicit per-endpoint policies; a shared Valkey-backed adapter is required before horizontally scaled production deployment.
- 2026-08-25: Phase 01C-B security-control tests exposed stale built workspace output when API tests were invoked directly after changing `@slotlyflow/config`. Rebuilding the shared config package resolved the runtime export mismatch; normal Turbo verification builds dependencies first.
- 2026-08-25: Corrected the PostgreSQL integration fixture to reset both `public` and Drizzle's migration-history schema. Dropping only `public` left migration records intact, causing an empty schema to be treated as fully migrated. No migration SQL was changed.
- 2026-08-25: Completed the Phase 01C-B authentication HTTP and PostgreSQL test coverage. The suite now verifies CSRF proof failures (including malformed tokens), endpoint-specific HTTP rate limits, non-enumerating login and password-recovery behavior, verification/reset expiry and replay, session lifecycle/revocation, safe response shapes, hashed persistence, and audit records without secrets. The process-local limiter exposes a reset method solely to isolate tests. Live execution remains pending an explicitly isolated `DATABASE_URL` ending in `_test`.
- 2026-08-25: Kept destructive PostgreSQL integration fixtures on the explicit `db:test` workflow rather than the ordinary workspace `test` command. This prevents concurrent schema resets from racing the API HTTP e2e suite; both suites remain available for live isolated-database verification.
- 2026-08-25: Fixed Phase 01C-B E2E runtime dependency injection by making every `AuthService` and `AuthController` dependency explicit at runtime. Vitest's transform did not reliably provide TypeScript design-time constructor metadata, leaving the password service and controller dependencies undefined. Added a real Nest/Fastify bootstrap regression test for `GET /auth/csrf`, and declared `DATABASE_URL` as a Turbo test-task environment input so an explicitly supplied isolated test URL reaches the API e2e task without being hard-coded.
- 2026-08-25: Corrected two E2E-discovered safe-error defects: nullish-coalescing/ternary precedence incorrectly translated explicit authentication/CSRF codes to `DEPENDENCY_UNAVAILABLE`, and Drizzle's wrapped PostgreSQL unique-constraint error was not recognized during duplicate registration. Client responses remain sanitized; focused regression coverage verifies typed error preservation.
- 2026-08-25: Replaced unsafe non-null assertions in the PostgreSQL authentication integration fixtures with explicit inserted-row guards, and made the E2E SameSite assertion type-safe. These are test-only static-safety fixes; authentication behavior and migrations are unchanged.
- 2026-08-25: Replaced the remaining API E2E non-null assertions with explicit cookie, fixture-token, and persisted-record guards so lint and strict typechecking enforce the test setup assumptions without weakening assertions.
- 2026-08-25: Phase 01C-C adds Google OIDC through a normalized provider boundary backed by the maintained `openid-client` dependency already present in the API. The durable OAuth state stores only SHA-256 hashes of state, nonce, and the PKCE verifier; raw nonce/verifier values use short-lived HttpOnly callback-scoped cookies. Google validation remains in the adapter, and no provider tokens are persisted.
- 2026-08-25: Google identity resolution uses the existing User -> AuthenticationIdentity -> Session model. A provider-verified Google email may link only to a matching already-verified local email; unverified local accounts are rejected pending a future explicit linking flow. Google-only users retain a null password hash. Phase 01C-C automated coverage uses a fake provider boundary; live Google verification remains pending manually supplied credentials, and isolated PostgreSQL verification remains pending an available `_test` URL.
- 2026-08-25: Real isolated-database E2E verification found that Nest/Fastify was returning a default 200 after the Google initiation and successful callback handlers awaited `reply.redirect`. Both handlers now explicitly send a 302 with the configured location after cookie updates; callback transaction cookies are cleared before sending and also on failure.
- 2026-08-25: Phase 01C-D1 adds only the Sign In route. It uses the existing API CSRF/login endpoints with browser cookie credentials and redirects successful sessions to the existing root foundation state because no authenticated application shell is approved yet. The API CORS adapter now permits credentials only when an origin is already explicitly allow-listed, which is required for separate web/API origins.
- 2026-08-25: The Sign In page uses a transparent derivative of the official SlotlyFlow documentation logo while preserving the original source artwork. No official Google G asset exists locally, so the Google action uses its required text and backend route without fabricating the Google mark; add an approved official asset in a future asset-only follow-up if brand guidance requires it.
- 2026-08-25: Standardized local startup configuration without adding a dependency: the API and database tooling use Node's native environment-file support for an ignored root `.env.local`, while Next.js uses an isolated browser-only `apps/web/.env.local`. The web API origin is now required and validated, eliminating the unsafe same-origin OAuth fallback. Local ports remain fixed at web `3000`, API `3001`, and SlotlyFlow PostgreSQL host port `5433`; Phase 01 remains `IN_PROGRESS`.
- 2026-08-25: Corrected the native environment-loader invocation after live `pnpm dev` exposed a `tsx` CLI parsing conflict between its `watch` subcommand and Node's `--env-file-if-exists` flag. API development now uses Node's native `--watch --import tsx` execution path; database migration and integration entrypoints use the same explicit Node loader form.
- 2026-08-25: Phase 01C-D2 adds only the Create Account route. Email/password registration follows the existing CSRF-protected `POST /auth/register` contract, enforces the backend's 12–256 character password limits client-side, coalesces duplicate in-flight submissions, accepts only the typed `EMAIL_VERIFICATION_REQUIRED` success response, and routes to the future `/verify-email` checkpoint without creating a session or implementing that page. Google registration reuses the existing `/auth/google` flow. Phase 01 and the remaining authentication UI checkpoints stay `IN_PROGRESS`.
- 2026-08-25: Phase 01C-D3 inspection found no resend-verification HTTP contract or email-delivery adapter. Registration creates a hashed verification-token record but the public response intentionally contains neither the token nor a delivery guarantee. A complete resend experience therefore requires an explicit public endpoint and delivery-abstraction decision; the Verify Email UI must not fabricate either or claim that mail was sent.
- 2026-08-25: The approved Phase 01C-D3 backend prerequisite is complete. A SlotlyFlow-owned `EmailProvider` boundary now delivers verification mail through a provider-neutral SMTP adapter, with Mailpit as the isolated local Compose sink. Registration persists the user and hashed token before attempting delivery; provider failure is audited without token material and returns a controlled dependency failure so resend can recover later. `POST /auth/email/resend` is CSRF-protected, rate-limited by requester and normalized-email hash, returns the same `ACCEPTED` response for every syntactically valid account state, supersedes prior active tokens only for eligible unverified password accounts, and never returns/logs a raw token. Verify Email UI remains unimplemented and Phase 01 remains `IN_PROGRESS`.
